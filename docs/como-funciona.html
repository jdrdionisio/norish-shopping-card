Norish Shopping Card

Como funciona o cartão de lista de compras estilo Bring! para Home Assistant, assente nas entidades to-do da integração hass-norish.

v1.0.0 · github.com/jdrdionisio/norish-shopping-card

1. Visão geral

O cartão é uma camada de interface. Não conhece o Norish, não tem chave de API e não faz pedidos HTTP ao servidor de receitas. Lê e escreve entidades to-do do Home Assistant, e é a integração que trata do resto.

Há duas direções de tráfego, e cada uma usa um mecanismo diferente:

DireçãoMecanismoPorquê

2. Porque um cartão e não uma integração

Porque os dados já existem como entidades. A integração hass-norish cria uma entidade to-do por loja mais uma para os itens sem loja. Uma integração nova obrigaria a repetir autenticação, limites de pedidos e serialização que a existente já resolve — e colocaria uma chave de API num ficheiro de JavaScript.

regra Se o dado já está exposto como entidade, o cartão conduz a entidade. A chave fica no servidor, não há CORS e herda-se a lógica de retry da integração.

3. As entidades em uso

Nesta instância (HA 2026.11.0) o cartão descobre pelo prefixo todo.norish_:

EntidadeNomeLista
todo.norish_unsortedUnsortedItens sem loja (aparece sempre primeiro)
todo.norish_auchanAuchanItens da loja Auchan
todo.norish_continenteContinenteItens da loja Continente
todo.norish_lidlLidlItens da loja Lidl
todo.norish_mercadonaMercadonaItens da loja Mercadona

O prefixo é o único critério fiável: a instância tem outras listas (todo.lista_de_compras, todo.compras, do Bring) que não podem aparecer no cartão. Cada entidade declara supported_features = 7 — criar (1) + apagar (2) + editar (4) — ou seja, sem reordenar (8) e sem descrição (64). O cartão esconde o que a entidade não sabe fazer em vez de mostrar botões que falham.

4. Ler a lista — subscrição websocket

Não há polling. O cartão abre uma subscrição por loja e recebe a lista sempre que ela muda. A subscrição também entrega imediatamente a lista inicial, por isso serve de primeiro carregamento:

hass.connection.subscribeMessage(
  (msg) => {
    this._byEntity[entity_id] = msg.items || [];   // e.g. [{uid, summary, status}]
    this._renderStores();                          // atualiza as contagens no seletor
    this._render();                                // redesenha a lista visível
  },
  { type: "todo/item/subscribe", entity_id }
).then((unsub) => { this._unsubs[entity_id] = unsub; });

O cartão subscreve a todas as lojas ao mesmo tempo, não só à visível — é assim que o seletor mostra a contagem de itens ativos de cada loja em tempo real. Quando uma loja nova aparece (ou desaparece) na instância, a assinatura do conjunto de entidades muda e as subscrições são refeitas.

Forma de cada item no fio:

{ "uid": "ac8bfdc4-f02f-4f7e-996b-d26d9b5bb2ea",
  "summary": "2 kg batatas",
  "status": "needs_action" }     // ou "completed"

5. Escrever — os serviços to-do

Cada funcionalidade mapeia diretamente num serviço do componente todo:

Ação no cartãoServiçoDados
Adicionar item (Enter)todo.add_item{entity_id, item:"texto"}
Marcar/desmarcar feitatodo.update_item{entity_id, item:uid, status:"completed"|"needs_action"}
Editar o textotodo.update_item{entity_id, item:uid, rename:"novo texto"}
Apagar itemtodo.remove_item{entity_id, item:uid}
Limpar concluídostodo.remove_completed_items{entity_id}

Marcar e editar usam o mesmo serviço, mas o cartão envia-os em chamadas separadas:

_toggle(uid, checked) {
  this._hass.callService("todo", "update_item", {
    entity_id: this._selected, item: uid,
    status: checked ? "completed" : "needs_action",
  });
}

_commitEdit(uid, texto) {
  this._hass.callService("todo", "update_item", {
    entity_id: this._selected, item: uid, rename: texto,
  });
}
Porquê separadas: na hass-norish, uma única chamada com rename e status ao mesmo tempo responde HTTP 200 mas só aplica o rename — o status fica no valor antigo. Enviar as duas operações em chamadas distintas é correto em qualquer integração e evita o problema.

6. Renderização e reatividade

Três decisões explicam o comportamento do cartão:

O set hass dispara a cada mudança de estado

Num HA real isso acontece dezenas de vezes por minuto. Por isso o cartão nunca reconstrói o shadow DOM nesse setter: só reconstrói quando o conjunto de entidades muda (comparado por assinatura), e redesenha a lista apenas quando chega um push da subscrição.

O campo de adicionar vive fora da parte redesenhada

É o que permite escrever um item enquanto chegam atualizações sem perder o foco nem o cursor.

<div class="card">
  <div class="head">   título + seletor de loja   </div>
  <div class="add">    <input> + botão +          </div>   <-- nunca redesenhado
  <div class="list">   itens ativos               </div>   <-- redesenhado a cada push
  ...
</div>

Rede de segurança após cada escrita

A integração refresca o coordenador depois de cada mutação, mas essa ida-e-volta pode demorar. O cartão relê a lista via todo/item/list aos ~0,5 s e ~1,6 s, para o ecrã assentar mesmo que um push se perca.

Os eventos são tratados por delegação nos contentores da lista (um change para as caixas, click para apagar/editar, keydown+focusout para o nome), em vez de religar ouvintes a cada redesenho. As cores vêm todas de variáveis de tema do HA (--primary-color, --card-background-color, --divider-color…), por isso o cartão acompanha o tema claro ou escuro.

7. Funcionalidades, uma a uma

Adicionar

Escrever e premi Enter (ou o botão +). O campo limpa-se de imediato e o item aparece quando o push chega. O Norish volta a interpretar o texto, por isso 2 kg batatas pode voltar normalizado.

Marcar feita

A caixa envia status. O item sai da lista ativa e entra na secção concluídos, riscado.

Editar

Tocar no texto transforma-o num campo editável. Enter grava, Esc cancela, sair do campo também grava.

Apagar

O ✕ remove o item pelo uid.

Limpar concluídos

Um serviço para toda a lista, em vez de N remoções.

Seletor com contagens

Cada opção mostra os itens ativos dessa loja, ex. Mercadona (3). Unsorted aparece sempre primeiro.

9. Limitações conhecidas

  • Criar lojas não é possível pelo cartão. As lojas vivem na app Norish; a integração só as descobre. O cartão faz CRUD de itens, nunca de listas.
  • Sem arrastar para reordenar. A entidade não expõe MOVE_TODO_ITEM, por isso a função não existe.
  • Sem imagens, por opção. O cartão é só texto.
  • O texto pode voltar alterado. O servidor Norish reanalisa quantidade e unidade ao gravar.

11. Verificação na instância real

Antes de publicar, o caminho de dados foi exercitado contra o HA do utilizador (2026.11.0), com um item descartável que foi apagado no fim. Saídas reais:

Adicionar, ler a forma do item, editar, marcar, apagar

POST /api/services/todo/add_item            -> HTTP 200
POST /api/services/todo/get_items?return_response
POST /api/services/todo/update_item (rename)  -> HTTP 200
POST /api/services/todo/update_item (status)  -> HTTP 200
POST /api/services/todo/remove_completed_items -> HTTP 200
POST /api/services/todo/remove_item           -> HTTP 200
{ "service_response": { "todo.norish_unsorted": { "items": [ { "summary": "TESTE cartao — renomeado", "uid": "ac8bfdc4-f02f-4f7e-996b-d26d9b5bb2ea", "status": "completed" } ] } } } lista final: items: [] (item de teste removido)
O que ficou provado: os nomes dos serviços, a forma {summary, uid, status}, o rename, o toggle, as remoções e o estado final limpo. E também o caso combinado: uma só chamada com rename+status devolve 200 e deixa o status em needs_action — daí as chamadas separadas no cartão.
