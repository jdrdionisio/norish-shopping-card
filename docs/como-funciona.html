1Cliente, servidor e protocolo

Tudo o que se segue assenta numa divisão simples de papéis. Um cliente inicia pedidos; um servidor espera por eles e responde. O cliente nunca «entra» no servidor: pergunta, e o servidor decide o que devolve.

Um protocolo é o acordo sobre a forma dessas mensagens — que texto vai, em que ordem, com que campos, e o que cada resposta significa. Sem acordo, dois programas conseguem falar um com o outro na rede e mesmo assim não se entendem.

Neste sistema há vários clientes e servidores empilhados:

Browser
é cliente (do HA)
↔
Home Assistant
é servidor do browser
e cliente do Norish
↔
Norish
é servidor da sua API

O cartão corre no browser. O browser fala com o Home Assistant. O Home Assistant fala com o Norish. Nunca o browser fala diretamente com o Norish — e o porquê disso é o tema dos capítulos 5 e 24.

O detalhe que vale a pena guardar: o Home Assistant é ao mesmo tempo servidor (para o browser) e cliente (para o Norish). Essa dupla personalidade é o que lhe permite ser o intermediário — e é o que mantém a chave da API fora do browser.

2Um pedido HTTP por dentro

HTTP é o protocolo clássico de pedido-resposta da Web. Um pedido tem sempre esta anatomia:

ParteO que éExemplo real deste projeto
MétodoO verbo: que tipo de operação se pretende. GET (ler), POST (criar/agir), DELETE (apagar)
CaminhoQual recurso, dentro do servidor. /api/services/todo/add_item
CabeçalhosMetadados: quem sou, que formato aceito, que formato envio. Authorization: Bearer <token>
CorpoO conteúdo, quando há. {"entity_id":"todo.norish_unsorted","item":"Leite"}

A resposta tem sempre um código de estado, e o primeiro dígito diz a família:

CódigoSignificadoNeste projeto
2xxCorreu bem.200 — item adicionado.
3xxVai buscar isto a outro sítio (redirecionamento). 307 para /login quando a rota exige sessão.
4xxO pedido está mal ou não está autorizado. 401 chave inválida; 400 dados malformados.
5xxO servidor falhou.—
Porque isto importa Um 200 só diz que a mensagem foi aceite. Mais adiante (capítulo 21) vamos ver um serviço que responde 200 e não faz o que pedimos. Por isso a regra, aqui e em qualquer integração: confirmar sempre por leitura de volta, nunca pelo código da resposta.

Pedido real, à mão, para provar que o serviço existe:

$ curl -X POST "$HASS_URL/api/services/todo/add_item" \
    -H "Authorization: Bearer $HASS_TOKEN" \
    -H 'Content-Type: application/json' \
    -d '{"entity_id":"todo.norish_unsorted","item":"TESTE — apagar"}'
HTTP 200

Alguns serviços, além da resposta normal, podem devolver dados. Em HTTP puro isso tem de ser pedido explicitamente, com ?return_response — e é assim que se lê o conteúdo de uma lista sem ser o cartão a fazê-lo:

$ curl -X POST "$HASS_URL/api/services/todo/get_items?return_response" … \
    -d '{"entity_id":"todo.norish_unsorted"}'
{ "service_response": { "todo.norish_unsorted": { "items": [ { "summary": "TESTE — apagar", "uid": "ac8bfdc4-f02f-4f7e-996b-d26d9b5bb2ea", "status": "needs_action" } ] } } }

Três campos definem um item de lista, e o cartão vive deles: summary (o texto), uid (a identidade estável — é com ele que se apaga ou edita) e status (por fazer ou feito).

3TLS e o proxy inverso

O «S» de HTTPS é o TLS: uma camada que envolve o HTTP num canal cifrado e autenticado. O cliente confirma a identidade do servidor através de um certificado emitido por uma autoridade. Tudo o que descrevemos continua a acontecer dentro desse canal — o TLS é largura, não sintaxe.

Os endereços deste projeto são nomes, não IPs: https://homeassistant.jdrdionisio.com e https://norish.jdrdionisio.com. O DNS traduz o nome num endereço IP, e o TLS garante que o certificado corresponde ao nome — é por isso que o certificado é por nome e não por IP.

Uma proxy inversa é um servidor que fica à frente de outro: recebe o pedido em nome da aplicação, termina o TLS e reencaminha-o. Do ponto de vista do cliente, a proxy é o servidor.

Browser
→TLS
Proxy inversa
termina TLS, /api/… → app
→
Home Assistant
responde ao pedido

Para o cartão isto é irrelevante, e é essa a beleza: ele conhece apenas o caminho relativo /api/… e deixa o resto ao browser e à rede. É por isso que o mesmo cartão funciona em http://192.168.1.10:8123 e em https://homeassistant.jdrdionisio.com sem uma linha de configuração a mudar.

4Autenticação: chaves em cabeçalhos

Autenticar é provar quem somos. A forma mais simples na Web é um segredo partilhado que viaja em cada pedido. Nunca no corpo do URL — porque os URLs ficam registados em históricos, registos de proxies e referrers — mas num cabeçalho.

Dois estilos aparecem neste projeto:

Authorization: Bearer <token>     # o Home Assistant usa este
x-api-key: <chave>                 # o Norish usa este (cabeçalho à medida)
Conceito: de quem é o segredo Quem guarda o segredo decide a arquitetura. Aqui há dois segredos distintos: o token do Home Assistant, que o browser usa, e a chave da API do Norish, que o Home Assistant usa. O cartão só vê o primeiro. O segundo nunca sai do servidor — e por isso o cartão não pode falar com o Norish, mesmo que quisesse.

No código do cartão, o token é um detalhe invisível: o browser já está autenticado na sessão do HA, e as chamadas passam por hass.callService() e hass.connection, que trazem a autenticação com elas. O cartão nunca escreve um token em lado nenhum, e é assim que deve ser.

5Origem, mesma-origem e CORS

Este capítulo explica a limitação central do projeto. Vale a pena ser lido com atenção.

Uma origem é o trio esquema + máquina + porta:

https://homeassistant.jdrdionisio.com   <-- origem do dashboard
https://norish.jdrdionisio.com          <-- origem DIFERENTE

Os dois podem apontar para a mesma casa, talvez para o mesmo IP — e ainda assim são origens diferentes, porque os nomes são diferentes. A comparação é textual, não geográfica.

A política de mesma-origem é o mecanismo de segurança do browser: uma página carregada de uma origem não pode ler a resposta de um pedido feito a outra origem. Sem isto, uma página maliciosa qualquer poderia chamar a API do teu banco a partir de um separador aberto no teu browser, usando a tua sessão.

Mas a Web não vive de sites isolados, e por isso existe um mecanismo explícito de abertura: o CORS (Cross-Origin Resource Sharing). É um diálogo em que o servidor declara quem pode ler as suas respostas, através de cabeçalhos Access-Control-Allow-*.

Para pedidos que «não são simples» — por exemplo, os que trazem um cabeçalho personalizado como x-api-key — o browser não manda o pedido a sério de imediato. Envia primeiro um pedido de verificação com o método OPTIONS, a perguntar se pode:

$ curl -X OPTIONS https://norish.jdrdionisio.com/api/trpc/pantry.list \ -H "Origin: https://homeassistant.jdrdionisio.com" \ -H "Access-Control-Request-Method: GET" \ -H "Access-Control-Request-Headers: x-api-key" HTTP/2 204 (nenhum cabeçalho Access-Control-*)

O 204 é «recebi». A ausência total de Access-Control-Allow-Origin é o servidor a dizer, em silêncio, «não autorizo». O browser interpreta esse silêncio como recusa e bloqueia o pedido antes de o enviar — o que o programador vê na consola é um erro de CORS, não um erro do servidor.

Consequência para este cartão. Como o Norish não autoriza a origem do Home Assistant, o cartão não pode pedir nada ao Norish. E mesmo que autorizasse, a chave da API teria de estar no JavaScript do cartão — legível por quem abre as ferramentas do browser num dashboard. Conclusão: os dados do Norish têm de entrar pelo servidor do Home Assistant. É o que a integração faz, e é o que o sensor REST do capítulo 24 faz para a despensa.

6Polling e push

Se o cliente quer saber quando algo muda, há duas estratégias.

Polling — perguntar sempre

O cliente pergunta de tempos a tempos: «mudou?». É simples e funciona em HTTP puro. O custo é medível: 5 lojas × 1 pergunta a cada 10 segundos = 43 200 perguntas por dia, das quais a esmagadora maioria recebe «não». Pior: com um limite de 500 pedidos por hora no Norish, o polling sozinho esgotaria a quota.

Push — o servidor avisa

O cliente diz uma vez «quero saber dos itens desta lista» e fica à escuta. O servidor envia uma mensagem quando — e só quando — algo muda. Zero tráfego inútil, e a atualização é imediata em vez de «até 10 segundos depois».

A dificuldade do push é que o HTTP clássico não o permite: o protocolo é pedido-resposta e um servidor não tem como começar a falar. É por isso que existe o WebSocket.

7HTTP e WebSocket lado a lado

Um WebSocket começa como um pedido HTTP que pede uma promoção («upgrade»). Se o servidor aceitar, a ligação deixa de ser pedido-resposta e passa a ser um canal bidirecional aberto: qualquer um dos lados pode enviar mensagens, a qualquer momento, indefinidamente.

HTTPWebSocket
InícioCliente pergunta, servidor responde, fim.Um pedido de promoção, depois canal aberto.
Quem fala primeiroSó o cliente.Ambos, quando quiserem.
DuraçãoUma troca.Muitas mensagens enquanto durar.
Serve paraPedidos pontuais.Subscrições e eventos.
Neste projetoVerificação, scripts, sensor REST.Ler a lista em tempo real.

O protocolo WebSocket do Home Assistant tem uma gramática própria, e é simples: cada mensagem leva um id e um type. O id é o que permite ter vários pedidos em curso no mesmo canal sem os confundir.

MensagemSignificado
{"type":"result","id":N,"success":true}A resposta a uma mensagem nossa com o id N.
{"type":"event","id":N,"event":{…}}Um evento de uma subscrição do id N. Não foi pedido: chegou por si.
{"type":"error","id":N,"error":{…}}Falhou.

Eis a conversa verdadeira, capturada contra este servidor. <-- é o que o servidor enviou; --> o que nós enviámos:

<-- {"type": "auth_required", "ha_version": "2026.11.0"}
--> {"type": "auth", "access_token": "…"}
<-- {"type": "auth_ok", "ha_version": "2026.11.0"}

--> {"id": 1, "type": "todo/item/subscribe", "entity_id": "todo.norish_unsorted"}
<-- {"id": 1, "type": "result", "success": true, "result": null}
<-- {"id": 1, "type": "event", "event": {"items": []}}
     ^ push inicial: a subscrição serve de primeiro carregamento

--> {"id": 2, "type": "call_service", "domain": "todo", "service": "add_item",
     "service_data": {"entity_id": "todo.norish_unsorted", "item": "TESTE websocket — apagar"}}
<-- {"id": 1, "type": "event", "event": {"items": [
      {"summary": "TESTE websocket — apagar",
       "uid": "6bdeb3fa-92ed-41bd-b5f5-c6681251c755",
       "status": "needs_action", "due": null, "description": null, "completed": null}]}}
     ^ CHEGOU SOZINHO: ninguém o pediu, a subscrição empurrou-o
<-- {"id": 2, "type": "result", "success": true, "result": {"context": {…}}}

Três observações que valem ouro:

  • A primeira mensagem é sempre auth_required: o servidor apresenta-se e exige autenticação antes de qualquer outra coisa.
  • A subscrição devolve result e logo a seguir um event com a lista atual. Não é preciso um pedido separado para carregar pela primeira vez — o push inicial faz as duas coisas.
  • A mensagem com id: 1 (o evento) chega antes da mensagem com id: 2 (o resultado do serviço). Num canal bidirecional, a ordem de chegada não é a ordem de envio. Quem escrever um cliente tem de filtrar por id, nunca contar com a ordem — foi exatamente este detalhe que partiu o meu primeiro guião experimental.

8RPC: chamar funções pela rede

O HTTP+JSON pode ser usado de duas filosofias. No estilo REST, os endereços são substantivos (/groceries/42) e o método é o verbo. No estilo RPC (remote procedure call), chama-se uma função pelo nome e enviam-se argumentos — como uma chamada local, mas pela rede.

O Norish usa os dois. A API pública /api/v1 é REST. Já as operações que a própria aplicação usa são RPC, em tRPC, e o endereço é o nome da função:

/api/trpc/pantry.list
/api/trpc/ingredients.find
/api/trpc/groceries.toggle

O tRPC acrescenta dois pormenores. Escreve batch=1 porque permite agrupar várias chamadas numa só mensagem — e isso importa quando a chave é verificada uma vez por pedido:

{"0": {"json": {"name": "leite"}}}      // chamada 0, com os seus argumentos

E como parâmetro de URL vai codificado (o {" não pode viajar cru):

/api/trpc/ingredients.find?batch=1&input=%7B%220%22%3A%7B%22json%22%3A%7B%22name%22%3A%22leite%22%7D%7D%7D
Conceito: o nome da função é a superfície Em RPC, saber o nome de uma função é metade do trabalho. É por isso que, quando uma capacidade parece não existir, o caminho é ler o código do servidor à procura do nome — e não concluir que não existe. Foi assim que apareceu ingredients.find, que o Norish usa no seu próprio campo de compras e que não consta em lado nenhum da documentação pública.

9O Home Assistant por alto

Terminada a rede, entramos no segundo domínio. O Home Assistant tem duas metades muito diferentes:

Core — o servidor

Programa em Python. Mantém o estado de tudo, executa automações, fala com os dispositivos, expõe as APIs HTTP e WebSocket. É a memória e o cérebro.

Frontend — a interface

Programa no browser. Desenha os dashboards e conversa com o core pelas APIs. Não guarda estado próprio: o que mostra vem sempre do core.

Essa separação é a chave para entender o cartão. O cartão é frontend: não fala com dispositivos, não fala com o Norish, não tem memória. Todo o seu poder vem de ler o que o core lhe dá e pedir ao core para agir.

Cartão
frontend, no browser
↔
Core
Python, o estado
↔
Integrações
falam com o mundo

10A máquina de estados e as entidades

Tudo no Home Assistant gira à volta de uma única ideia: uma máquina de estados. Existe um objeto de estado por cada coisa que o sistema conhece, e existe um evento sempre que algo muda. Quem quiser saber, subscreve.

A unidade é a entidade. O seu nome, o entity_id, tem sempre duas partes separadas por um ponto:

todo  .  norish_mercadona
│        └── object_id: um nome único dentro do domínio
└── domain: que TIPO de coisa é

Pode ler-se como «o domínio é o que ela sabe fazer, o object_id é qual delas é». O cartão seleciona as entidades que lhe interessam pelo domínio e pelo prefixo do object_id:

Object.keys(this._hass.states).filter((e) => e.startsWith("todo.norish_"))

Uma entidade tem duas partes de dados. O estado é uma string — sempre, mesmo quando parece um número — e é o valor principal. Os atributos são um dicionário com tudo o resto:

$ curl $HASS_URL/api/states/todo.norish_mercadona -H "Authorization: Bearer …" { "entity_id": "todo.norish_mercadona", "state": "0", "attributes": { "friendly_name": "Norish Mercadona", "supported_features": 7 }, "last_changed": "2026-11-07T13:50:57.345602+00:00", "last_updated": "2026-11-07T13:50:57.345602+00:00" }

Três leituras deste pequeno JSON:

  • state: "0" — numa lista de tarefas o estado é o número de itens por fazer. É uma string por convenção do sistema, mas semanticamente um número.
  • friendly_name — o nome legível, o que aparece no ecrã. O cartão mostra Mercadona (limpa o prefixo «Norish ») e usa o entity_id para tudo o resto.
  • supported_features: 7 — ver o capítulo 12. Guarde-se a ideia: uma entidade declara o que sabe fazer.
Conceito: estado observável Repare-se que os itens não estão aqui. O estado de uma entidade é uma string e os atributos são pequenos. Uma lista de compras inteira não caberia neste modelo, e o HA resolve isso com um mecanismo à parte: a subscrição de itens (capítulo 12). É este o motivo pelo qual o cartão precisa do WebSocket e não se contenta com os atributos.

Um último ponto que causa muita confusão: entity_id não é unique_id. O primeiro é o endereço no sistema (e pode ser renomeado pelo utilizador); o segundo é a identidade interna que a integração atribui (e é por ele que o histórico sobrevive a mudanças de nome).

11Integrações: config entries e coordenadores

Uma integração é a peça que sabe falar com algo externo. No Home Assistant é uma pasta de Python, e uma regra vale a pena memorizar: o nome da pasta é o domínio.

custom_components/
└── norish/
    ├── manifest.json    ← a identidade: domain, versão, tipo
    ├── config_flow.py   ← o formulário de configuração
    ├── coordinator.py   ← quem pede os dados periodicamente
    ├── todo.py          ← quem cria as entidades de lista
    ├── sensor.py, calendar.py, …
    └── translations/

O manifest.json do hass-norish diz muito sobre o seu comportamento:

{
  "domain": "norish",
  "config_flow": true,
  "integration_type": "service",
  "iot_class": "cloud_polling",     <-- não é local, e é por polling
  "version": "1.8.0"
}

Quando o utilizador adiciona a integração, o HA cria uma config entry: o registo dessa configuração, com as credenciais e as opções. As entidades pertencem à config entry — e é por isso que apagar a config entry e voltar a criá-la perde o histórico, mesmo que o código seja o mesmo.

Como iot_class diz que é cloud_polling, alguém tem de ir buscar os dados de tempos a tempos. Esse alguém é o coordenador (DataUpdateCoordinator), um padrão do HA que faz três coisas:

  1. Pede os dados numa cadência própria (no hass-norish, 15 minutos por omissão).
  2. Guarda o resultado numa cache, para que as entidades não tenham de pedir nada quando alguém as lê.
  3. Avisa todas as entidades suas quando a cache muda — e as entidades, por sua vez, avisam a máquina de estados, que avisa o WebSocket, que avisa o cartão.

Vê-se aqui a cadeia completa de propagação de uma mudança:

Norish
os dados mudam
→poll
Coordenador
cache + cadência
→
Entidade
novo estado
→
Core
máquina de estados
→WebSocket
Cartão
redesenha
Uma limitação do polling que se vê no cartão. Como a integração atualiza a cada 15 minutos, uma alteração feita noutro telefone pode demorar a aparecer. É por isso que o hass-norish força um refresh imediato depois de cada escrita vinda do HA: a ação do utilizador merece uma atualização pronta, não uma espera de 15 minutos.

12Plataformas: como nasce uma entidade todo

Uma integração não cria entidades diretamente. Organiza-se em plataformas — uma por tipo de entidade. O hass-norish tem todo.py, sensor.py, calendar.py, camera.py e media_player.py. Cada ficheiro diz: «nas entidades deste tipo, eis as que eu crio».

No todo.py a decisão tomada é: uma entidade por loja, mais uma para os itens sem loja. É daí que vêm as entidades do capítulo 10.

entities.append(NorishStoreList(coordinator, entry, store_id=None, store_name="Unsorted"))
for store_id, store_name in stores.items():
    entities.append(NorishStoreList(coordinator, entry,
                                    store_id=store_id, store_name=store_name))

Dentro de cada entidade, a classe herda de TodoListEntity — a base que o HA fornece para listas de tarefas. Herdar dali dá o entity_id, o registo, o estado, tudo. A integração só preenche a parte específica:

class NorishStoreList(CoordinatorEntity, TodoListEntity):

    @property
    def todo_items(self) -> list[TodoItem]:
        """Os itens desta loja (ou os itens sem loja, se store_id for None)."""
        groceries = self.coordinator.data.get("groceries", [])
        if self.store_id is None:
            filtered = [g for g in groceries if not g.get("storeId")]
        else:
            filtered = [g for g in groceries if g.get("storeId") == self.store_id]
        return [_grocery_to_todo_item(g) for g in filtered]

E agora o capítulo 10 fica explicado. Os itens existem, mas não estão no estado. Vivem na todo_items da entidade, e chega-se a eles por um canal próprio — a subscrição:

hass.connection.subscribeMessage(cb, {type: "todo/item/subscribe", entity_id})

Do lado do servidor há um par correspondente, async_subscribe_updates: é a integração a inscrever-se para ser avisada quando os itens mudarem. Quando isso acontece, o servidor envia o event pelo WebSocket a todos os clientes inscritos. O cartão é apenas um desses clientes — o mesmo mecanismo que serve a página nativa de tarefas.

Por fim, a entidade declara o que sabe fazer, através de uma máscara de bits em supported_features. É um conceito útil: em vez de o cliente adivinhar ou testar, o servidor diz. O valor 7 do capítulo 10 decompõe-se assim:

BitValorSignificaEste cartão
CREATE_TODO_ITEM1Saber adicionar itensSim — campo de adicionar
DELETE_TODO_ITEM2Saber apagar itensSim — botão ✕
UPDATE_TODO_ITEM4Saber editar itensSim — renomear e marcar
MOVE_TODO_ITEM8Saber reordenarNão — sem arrastar
SET_DUE_DATE_ON_ITEM16Saber datas-limiteNão
SET_DESCRIPTION_ON_ITEM64Saber descriçõesNão

1+2+4 = 7. É por isso que o cartão não tem botão de arrastar: não é uma escolha de design, é a entidade que não oferece a capacidade. Um botão desses existiria para dar um erro — e uma limitação honesta é melhor que um botão que falha.

Conceito: o servidor declara, o cliente respeita Sempre que um cartão for feito sobre entidades existentes, o primeiro passo é ler supported_features e desenhar a interface depois. Ao contrário, o resultado são botões que parecem funcionar e devolvem erros.

13Serviços: a API de verbos

Ler o estado é passivo. Para agir, o HA tem os serviços — que a interface gráfica passou a chamar ações, mas que no código continuam service. Um serviço é uma operação nomeada, com dois níveis:

todo.add_item
│     │
│     └── o serviço (o verbo)
└── o domínio (sobre o tipo de coisa)

A chamada leva três coisas: o domínio, o serviço e os dados — onde vai sempre o entity_id do alvo.

hass.callService(domain, service, data)

hass.callService("todo", "update_item", {
  entity_id: "todo.norish_mercadona",
  item: "ac8bfdc4-…",          // o uid do item, não o texto
  status: "completed",
});

Note-se que item é o uid, não o texto visível. É a consequência natural do capítulo 2: identidades estáveis, não nomes. Dois itens podem chamar-se «leite»; só o uid distingue qual se está a marcar.

O conjunto de serviços todo disponíveis é pequeno e cobre exatamente o CRUD que o cartão promete:

Porque é que o cartão é simples. Todo o CRUD já existe como serviço oficial. O cartão não inventa protocolo nenhum: chama os verbos que o HA define e desenha o resultado. Metade do trabalho de um cartão é saber que os verbos já existem.

15Lovelace, dashboards e recursos

Um dashboard é, no fundo, uma lista de cartões. Cada cartão é uma caixa que sabe desenhar-se a si própria. Não há um «motor de layout» que entenda de compras: há caixas que se desenham.

Para que um cartão exista, o frontend tem de carregar o seu código. Isso faz-se por recursos — ficheiros JavaScript registados na configuração do dashboard:

Duas notas de bastidores. O caminho /hacsfiles/ é servido pelo HACS, uma integração cujo único trabalho é instalar e manter recursos de terceiros — não é magia, é um diretório servido pelo HA. 16Web Components: a linguagem dos cartões

Um cartão é um Web Component — uma capacidade que está no próprio browser, não numa biblioteca. Basta ensinar ao browser uma etiqueta nova:

class NorishShoppingCard extends HTMLElement {
  …
}

customElements.define("norish-shopping-card", NorishShoppingCard);

A partir daí, <norish-shopping-card> é uma etiqueta HTML válida, tratada como qualquer <div>. Não há framework, não há passo de compilação, não há dependências: o browser sabe fazer isto.

O segundo pilar é o shadow DOM. Cada componente pode ter uma árvore de elementos própria, isolada do resto da página:

this.attachShadow({ mode: "open" });
this.shadowRoot.innerHTML = `<style>.card { … }</style><div class="card">…</div>`;
Conceito: encapsulamento Sem shadow DOM, um <style> com .card dentro do cartão afetaria todos os .card da página — e o CSS do dashboard afetaria o cartão. Com shadow DOM, cada lado vive na sua bolha. É por isso que o cartão pode usar os nomes de classe que quiser sem medo, e é por isso que há dois problemas separados: as cores têm de vir de variáveis de tema (que atravessam o shadow DOM por serem propriedades CSS herdadas), enquanto tudo o resto fica isolado. 
.card {
  background: var(--ha-card-background, var(--card-background-color, #fff));
  color:      var(--primary-text-color, #212121);
  border: 1px solid var(--divider-color, rgba(0,0,0,.12));
}

Cada var(…, fallback) lê uma variável do tema do HA e usa o segundo valor se ela faltar. Resultado: o cartão acompanha o tema claro e o escuro sem uma linha de código a mais, e continua legível fora do HA — útil para a pré-visualização deste documento.

17O contrato de um cartão

Um cartão não é um programa que corre: é um objeto que o Home Assistant conduz. O HA chama três coisas, e a nossa parte é responder bem a elas.

1. O HA entrega a configuração — setConfig

setConfig(config) {
  this._config = Object.assign(
    { title: "Lista de compras", entities: null, warn_duplicates: true, pantry_entity: null },
    config || {}
  );
  this._sig = null;   // invalida: o conjunto de entidades tem de ser redescoberto
}

É aqui que se valida o YAML do utilizador. A regra prática: falhar alto e cedo. Uma opção com o tipo errado deve dar um erro claro agora, e não um comportamento estranho daqui a dez minutos.

if (config && config.entities && !Array.isArray(config.entities)) {
  throw new Error("norish-shopping-card: 'entities' must be a list of todo entity ids");
}

2. O HA entrega o mundo — set hass

hass é o objeto por onde o cartão vê o Home Assistant inteiro. As quatro portas que este cartão usa:

PortaO que dáUsada para
hass.statesO dicionário de todas as entidades e estadosDescobrir as listas e ler o sensor da despensa
hass.callService(domain, service, data)Executar um serviçoAdicionar, marcar, editar, apagar
hass.callWS(msg)Uma mensagem WebSocket com respostaReler a lista como rede de segurança
hass.connection.subscribeMessage(cb, msg)Uma subscrição contínuaReceber os itens em tempo real

E aqui está a armadilha fundamental de escrever cartões: set hass não é chamado uma vez. É chamado a cada mudança de estado de qualquer entidade da instância — dezenas de vezes por minuto, sem aviso. Código ingénuo que reconstrói o HTML neste setter destrói a interface continuamente: os campos perdem o foco, o cursor salta, o toque perde-se.

set hass(hass) {
  this._hass = hass;
  if (!hass || !hass.states) return;
  const ents = this._entities();
  const sig = ents.join("|");       // a assinatura do conjunto de entidades
  if (sig !== this._sig) {          // só reconstrói quando o CONJUNTO muda
    this._sig = sig;
    this._setup(ents);
  }
}

Guardar a referência a hass é sempre seguro. Reconstruir, só quando a lista de entidades muda — que no cartão significa: alguém criou uma loja nova.

3. O HA pergunta o tamanho — getCardSize

getCardSize() { return 8; }

É a dica para o layout estimar a altura antes de o cartão estar desenhado. É uma estimativa, não uma medida.

18Aparecer no seletor de cartões

Ao definir o elemento, o cartão passa a funcionar no YAML — mas ainda não aparece na lista visual de cartões. Para isso existe um registo simples:

window.customCards = window.customCards || [];
window.customCards.push({
  type: "norish-shopping-card",
  name: "Norish Shopping Card",
  description: "Lista de compras estilo Bring sobre as entidades to-do do Norish…",

O || [] não é ruído: vários cartões diferentes fazem o mesmo, e o primeiro a carregar pode encontrar a lista por criar.

E há a peça que faz tudo funcionar em produção: o recurso tem de estar registado uma vez, e o caminho tem de existir. Um caminho errado não dá um erro útil — dá um cartão que nunca aparece e um aviso vago na consola. É o erro mais comum de quem instala um cartão, e não tem nada a ver com o código do cartão.

20Ler: a subscrição, passo a passo

Cada passo, com o código ao lado da razão.

Passo 1 — Descobrir as entidades

_entities() {
  const configured = this._config.entities;
  if (Array.isArray(configured) && configured.length) {
    return configured.filter((e) => this._hass.states[e]);   // o que o utilizador fixou
  }
  const all = Object.keys(this._hass.states).filter((e) => e.startsWith(PREFIX));
  all.sort((a, b) => {
    const ua = a === PREFIX + "unsorted" ? 0 : 1;
    const ub = b === PREFIX + "unsorted" ? 0 : 1;
    return ua - ub || this._name(a).localeCompare(this._name(b), "pt");
  });
  return all;
}

O prefixo todo.norish_ é o único critério fiável: a instância tem outras listas de tarefas (todo.lista_de_compras, todo.compras, do Bring) que não pertencem a este cartão. A ordenação força Unsorted em primeiro lugar e depois ordena por nome em português.

Passo 2 — Abrir a subscrição

this._hass.connection.subscribeMessage(
  (msg) => {
    this._byEntity[e] = (msg && msg.items) || [];
    this._renderStores();     // as contagens do seletor
    this._render();           // a lista visível
  },
  { type: "todo/item/subscribe", entity_id: e }
);

subscribeMessage devolve uma promessa de função de cancelamento. Chamar essa função fecha a subscrição — e é obrigatório fazê-lo, senão cada mudança de loja deixaria uma subscrição órfã a receber dados para uma lista que já ninguém vê.

Promise.resolve(p)
  .then((unsub) => {
    if (this._pending[e]) this._unsubs[e] = unsub;
    else if (typeof unsub === "function") unsub();   // já não interessava
  })

Este cuidado — cancelar o que entretanto deixou de interessar — é o que evita a fuga de subscrições, o defeito clássico de interfaces vivas.

Passo 3 — O push faz o trabalho

Depois disto não há polling nenhum. Quando alguém marca um item no telefone, o Norish muda, o coordenador dá por isso, a entidade avisa, o HA envia um event, e a função acima corre. O cartão não perguntou nada.

Passo 4 — Uma rede de segurança, porque o mundo real atrasa

_refreshAfterMutation() {
  for (const delay of [500, 1600]) {
    window.setTimeout(() => {
      … this._hass.callWS({ type: "todo/item/list", entity_id: e }) …
    }, delay);
  }
}

A integração força um refresh depois de cada escrita, mas essa viagem tem várias etapas. Este reler tardio — duas vezes, a meio segundo e a segundo e meio — é a admissão de que o push pode atrasar e de que o ecrã não deve ficar dessincronizado por isso. Duas tentativas porque uma só falha nos casos lentos, e mais do que duas é ruído.

21Escrever: serviços, e uma armadilha real

As escritas usam os verbos do capítulo 13. Mas há um detalhe que só se descobre a testar, e que justifica uma decisão que à primeira vista parecia estranha.

Marcar e editar usam o mesmo serviço, todo.update_item — um com status, outro com rename. A tentação é juntar os dois numa só chamada. Eis o que aconteceu quando o testei:

$ curl -X POST "$HASS_URL/api/services/todo/update_item" … \
   -d '{"entity_id":"todo.norish_unsorted","item":"ac8bfdc4-…",
        "rename":"TESTE — renomeado","status":"completed"}'

HTTP 200

$ curl -X POST "$HASS_URL/api/services/todo/get_items?return_response" … 
{ "summary": "TESTE — renomeado", "uid": "ac8bfdc4-…",
  "status": "needs_action" }            <-- o status NÃO mudou

Um 200 impecável, o nome alterado, e o estado intacto. Na integração, a lógica aplica o rename e depois compara o estado — mas a leitura do item anterior já não corresponde ao que acabou de ser escrito, e o toggle perde-se. O utilizador veria o item renomeado e por marcar.

A solução é o que o cartão faz: uma chamada por intenção.

_toggle(uid, checked) {
  this._hass.callService("todo", "update_item", {
    entity_id: this._selected, item: uid,
    status: checked ? "completed" : "needs_action",
  });
}

_commitEdit(uid, texto) {
  this._hass.callService("todo", "update_item", {
    entity_id: this._selected, item: uid, rename: texto,
  });
}
Conceito: uma intenção, uma chamada Uma chamada = uma intenção = um resultado verificável. Juntar duas alterações independentes num só pedido cria uma transação implícita que o servidor pode não honrar, e um 200 deixa de significar «está feito». Separar é mais pedidos e muito menos mistério — e é mais correto em qualquer integração, não só nesta.

22O modelo de renderização

Três decisões explicam todo o comportamento visual do cartão.

O esqueleto constrói-se uma vez; a lista redesenha-se muitas

<div class="card">
  <div class="head">    título + seletor de loja          </div>
  <div class="add">     <input> + botão +                 </div>   ← nunca redesenhado
  <div class="warn">    aviso de duplicados               </div>
  <div class="list">    itens ativos                       </div>   ← redesenhado a cada push
  <div class="donebar"> mostrar concluídos · limpar        </div>
  <div class="done">    itens concluídos                   </div>
</div>

O campo de texto vive fora da zona redesenhada. É o que permite escrever um item enquanto chegam atualizações, sem perder o foco nem o cursor. É uma decisão de arquitetura com consequências imediatas para quem usa.

Eventos delegados, não religados

for (const host of [this.$.list, this.$.doneList]) {
  host.addEventListener("change", (ev) => {
    const chk = ev.target.closest("input.chk");
    if (chk) this._toggle(chk.dataset.uid, chk.checked);
  });
  host.addEventListener("click", (ev) => {
    const del = ev.target.closest("button.del");
    if (del) { this._remove(del.dataset.uid); return; }
    const sum = ev.target.closest(".summary");
    if (sum) this._startEdit(sum.dataset.uid);
  });
}

Dois ouvintes no contentor, para todos os itens que existam agora e no futuro. Se a lista se redesenha, os ouvintes continuam válidos — não é preciso religar nada a cada renderização. Sem isto, cada push deixaria os botões mortos.

Estado de edição por identidade, não por índice

Ao entrar em edição, o cartão guarda o uid do item a editar. Depois de redesenhar, procura esse uid e devolve-lhe o foco:

if (this._editing) {
  const inp = this.shadowRoot.querySelector(
    `input.edit[data-uid="${CSS.escape(this._editing)}"]`
  );
  if (inp) {
    inp.focus();
    inp.setSelectionRange(inp.value.length, inp.value.length);
  } else {
    this._editing = null;      // o item desapareceu entretanto
  }
}

Guardar a posição («linha 3») seria frágil: basta um push para a lista mudar de ordem e o foco aterrar no item errado. Guardar a identidade é estável — a mesma ideia do uid no capítulo 2, a reaparecer nove capítulos depois.

23Deteção de duplicados

O objetivo é avisar antes de criar algo que já existe. A dificuldade é que «existir» não é uma igualdade de texto: «2 kg batatas» e «batatas» são a mesma coisa, «ovo» e «Ovos» também, e «leitinho» não é «leite».

Normalizar antes de comparar

_norm(s) {
  return String(s)
    .normalize("NFD").replace(/[\u0300-\u036f]/g, "")   // remove acentos (água → agua)
    .toLowerCase()
    .replace(/([0-9])([a-z])/g, "$1 $2")                // 2kg → 2 kg
    .replace(/[^a-z0-9]+/g, " ")                        // pontuação fora
    .trim();
}

_core(s) {                       // e depois o que é comum a todas as escritas
  const toks = this._norm(s).split(" ").filter(Boolean);
  while (toks.length > 1 &&
         (/^\d+([.,]\d+)?$/.test(toks[0]) || LEAD_NOISE.has(toks[0]))) {
    toks.shift();                // deita fora "2", "kg", "de", "l", "pacote"…
  }
  return toks.join(" ");
}

O conjunto LEAD_NOISE tem de conter unidades em português e em inglês — porque o Norish normaliza unidades para inglês ao gravar (fatias torna-se slice). Esquecer isto deixa metade das comparações a falhar.

_norm("1,5 l Água")   → "1 5 l agua"
_core("1,5 l Água")   → "agua"          quantidade e unidade caem
_core("2kg batatas")  → "batatas"       "2kg" separa-se em "2 kg"

Comparar em degraus, do certo ao tolerante

_matches(q, key) {
  // singular grosseiro (plural em -s), para "ovo" encontrar "Ovos"
  const sing = (w) => (w.length >= 4 && w.endsWith("s") ? w.slice(0, -1) : w);
  const qw = q.split(" ").map(sing);
  const kw = key.split(" ").map(sing);
  const qs = qw.join(" ");
  const ks = kw.join(" ");

  if (qs === ks) return true;                        // igual
  if (kw.includes(qs) || qw.includes(ks)) return true;  // palavra inteira
  if (qs.length >= 4 && (ks.startsWith(qs + " ") || qs.startsWith(ks + " "))) return true;
  const setK = new Set(kw), setQ = new Set(qw);
  const subset = (a, b) => a.length > 0 && a.every((t) => t.length >= 2 && b.has(t));
  return subset(qw, setK) || subset(kw, setQ);       // todas as palavras de um lado
}

Resultados reais do testador, sobre uma lista com «Leite meio-gordo», «2 kg batatas», «Azeite» e «Ovos»:

"leite"          → Leite meio-gordo   (Unsorted)
"LEITE MEIO GORDO" → Leite meio-gordo
"leite gordo"    → Leite meio-gordo   (subconjunto de palavras)
"ovo"            → Ovos               (singular/plural)
"2kg batatas"    → 2 kg batatas       (Lidl)
"batatas"        → 2 kg batatas       (Lidl)
"azeite virgem"  → Azeite             (Lidl)
"leitinho"       → (nada)             sem falso positivo
"cebola"         → (nada)
Conceito: precisão contra cobertura Cada regra acrescentada aumenta a cobertura e arrisca falsos positivos. Um aviso de duplicados ruidoso é pior que nenhum: o utilizador aprende a ignorá-lo. Por isso o mínimo de três caracteres, o mínimo de duas letras por palavra, e a preferência por não avisar em vez de avisar errado — e por isso também nunca bloqueia: um segundo «leite» é, às vezes, exatamente o que se quer.

24A despensa, e uma correção importante

A segunda verificação é contra a despensa do Norish — o «que temos em casa». Aqui houve duas descobertas que mudam o que se deve dizer sobre este cartão.

Descoberta 1 — o Norish já funde duplicados

Fui verificar, adicionando deliberadamente o mesmo item duas vezes:

add 'TESTE merge — apagar'   → HTTP 200
  [{"summary": "TESTE merge — apagar", "uid": "1e0fe2c6-…", "status": "needs_action"}]

add 'TESTE merge — apagar'   → HTTP 200
  [{"summary": "2× TESTE merge — apagar", "uid": "1e0fe2c6-…", "status": "needs_action"}]
                ↑ mesmo uid, quantidade somada — não nasceu uma linha nova

add '2 kg TESTE merge — apagar'
  [{"summary": "2 kg TESTE merge — apagar", "uid": "015e5f23-…"},
   {"summary": "2× TESTE merge — apagar",   "uid": "1e0fe2c6-…"}]
                ↑ com quantidade explícita, aí sim é um item distinto
Correção ao que este documento dizia antes. A preocupação de «criar itens que já existem» está, em grande parte, já resolvida pelo próprio Norish: adicionar um nome repetido não cria uma linha duplicada — incrementa a quantidade no item existente («2×»), mantendo o mesmo uid. O aviso do cartão passa a ser, por isso, sobre consciência — saber antes de carregar em Enter, em vez de descobrir depois — em vez de sobre impedir uma duplicação que o servidor já evita.

Descoberta 2 — a despensa existe, mas não está no Home Assistant

No tRPC do Norish existem procedimentos que o /api/v1 público não expõe, e a chave da API autentica lá. Verificados contra este servidor, todos 200:

ProcedimentoO que devolve
ingredients.findnome → ingredientId, ou null. É o que o próprio Norish usa no campo das compras enquanto se escreve.
ingredients.listpesquisa paginada no catálogo (nomes, aliases, traduções).
pantry.lista despensa da família — 35 itens neste caso.
pantry.suggestionsalimentos usados pelas receitas que a despensa não cobre.
GET /api/trpc/ingredients.find?batch=1&input=…{"name":"leite"} → HTTP 200 {"ingredientId":"dda78de0-ee0f-4c4e-aa05-14a6949ccd6d"} o mesmo com "mareleite" → HTTP 200 null GET /api/trpc/pantry.list → HTTP 200 {"name":"butter", "localeNames":{"pt":"manteiga"}} {"name":"carrot", "localeNames":{"pt":"cenoura"}} {"name":"breadcrumbs", "localeNames":{"pt":"pão ralado"}}

O cartão não pode chamar isto (capítulo 5), e por isso os dados têm de entrar pelo servidor. A ponte é um sensor REST no configuration.yaml: o Home Assistant vai buscar a despensa, a chave fica no secrets.yaml, e o cartão limita-se a ler o atributo.

rest:
  - resource: "https://norish.jdrdionisio.com/api/trpc/pantry.list?batch=1&input=%7B%220%22%3A%7B%22json%22%3Anull%7D%7D"
    headers:
      x-api-key: !secret norish_api_key
    scan_interval: 1800            # 30 min: a despensa muda pouco, e há um limite de 500 pedidos/h
    sensor:
      - name: "Norish Pantry"
        value_template: "{{ value_json[0].result.data.json | length }}"
        json_attributes_path: "$[0].result.data.json"
        json_attributes: [name, localeNames]

E no cartão basta apontar para ele:

type: custom:norish-shopping-card
title: Lista de compras
pantry_entity: sensor.norish_pantry

Um pormenor que parece um detalhe e não é: a despensa guarda nomes em inglês com traduções. A correspondência tem de usar localeNames.pt, senão «manteiga» nunca encontra «butter».

25Limitações

  • Criar lojas não é possível pelo cartão. As lojas são listas no Norish, geridas na aplicação; a integração só as descobre. O cartão faz CRUD de itens. Não é uma falha do cartão: é onde a fronteira está.
  • Sem arrastar para reordenar. A entidade não declara MOVE_TODO_ITEM (capítulo 12).
  • A atualização depende de três saltos. Norish → coordenador → entidade → WebSocket → cartão. O refresh forçado após escrita encurta-o, mas não o elimina.
  • O texto pode voltar alterado. O servidor Norish reanalisa quantidade e unidade ao gravar: escrever «2 kg batatas» pode devolver «2× batatas».
  • A chave da API tem quota. 500 pedidos por hora, e a chave é desativada ao exceder, respondendo 401 como se fosse inválida — o que torna o erro enganador. Nada no cartão consome quota (usa o HA), mas uma pesquisa por tecla contra o Norish esgotaria a quota em minutos; daí o intervalo de 30 minutos no sensor.
  • Sem imagens, por opção.

28Glossário

TermoEm uma linha
HTTPProtocolo de pedido-resposta da Web. Cliente pergunta, servidor responde, fim.
WebSocketCanal bidirecional aberto, que começa como um pedido HTTP e deixa de o ser.
TLSA camada que cifra e autentica o canal. O «S» de HTTPS.
DNSTraduz um nome de máquina num endereço IP.
Proxy inversaServidor à frente de outro; representa-o perante os clientes.
OrigemTrio esquema+máquina+porta. Comparado textualmente.
CORSO mecanismo pelo qual um servidor autoriza outra origem a ler as suas respostas.
PreflightO OPTIONS que o browser envia antes de um pedido «não simples».
Polling / pushPerguntar sempre / ser avisado quando muda.
RPCChamar funções pelo nome através da rede. O tRPC do Norish.
EntidadeA unidade de estado do HA: domain.object_id, um estado (string) e atributos.
Máquina de estadosO core do HA: um valor por entidade, e um evento a cada mudança.
IntegraçãoA peça que fala com algo externo. Uma pasta em custom_components/; a pasta é o domínio.
Config entryO registo da configuração de uma integração. As entidades pertencem-lhe.
CoordenadorQuem pede os dados periodicamente, guarda em cache e avisa as entidades.
PlataformaA parte de uma integração que cria um tipo de entidade (o todo.py).
Serviço / açãoUma operação nomeada do HA, chamada com domain.service.
supported_featuresMáscara de bits por onde a entidade declara o que sabe fazer.
LovelaceA camada de dashboards do HA. Um dashboard é uma lista de cartões.
RecursoUm ficheiro JavaScript registado no dashboard para o frontend carregar.
Web ComponentUma etiqueta HTML definida pelo programador, nativa do browser.
Shadow DOMUma árvore de elementos e estilos isolada do resto da página.
hassO objeto que o HA entrega ao cartão: estados, serviços, WebSocket.
uidIdentidade estável de um item de lista. É por ele que se edita e apaga.
